# Excavation Video Lab
## Техническое задание для Cursor: локальный прототип видеохронометража экскавации

**Версия:** 1.0 · **Дата:** 9 октября 2026 года  
**Первый результат:** обучаемая детекция техники и ковша, трекинг и проверяемое видео с результатами.  
**Следующее расширение:** кандидаты событий разгрузки, проверка человеком и статистика по заездам самосвалов.

> Это спецификация будущего приложения, а не описание уже обученной модели. Численные настройки ниже — стартовые параметры эксперимента; критерии качества — цели, а не обещание результата. Исходный MP4, разметка и результаты обучения в комплект не входят.

## 0. Ключевое решение

Создать отдельный небольшой Python-проект с локальным веб-интерфейсом. Не использовать код или ограничения других проектов пользователя как обязательную основу.

**Стек:** RF-DETR Small / Nano + PyTorch → ByteTrack из пакета `trackers` → собственная логика привязки ковша и кузова → страницы Jinja2 на localhost-сервере Starlette. Разметка — в CVAT Community; обмен — COCO JSON. Видео — FFmpeg/ffprobe, PyAV и OpenCV. Метаданные — SQLite, массивы результатов — Parquet, пользовательские выгрузки — CSV.

**Не обучать нейросеть с нуля.** Дообучать готовые веса RF-DETR на собственных четырёх классах. Не считать исходный COCO-checkpoint готовым детектором ковша и карьерной техники.

Разделить разработку на два продукта:

| Версия | Обязательный результат | Чего в ней ещё нет |
|---|---|---|
| **v0.1 — Detection Lab** | Импорт видео, подготовка разметки, дообучение, оценка, детекция четырёх классов, трекинг, траектория ковша, просмотр и экспорт | Автоматически подтверждённых разгрузок, причин простоя, производственной точности на новых ракурсах |
| **v0.2 — Cycle Review** | Экспериментальные события разгрузки, заезды самосвалов, ручное подтверждение и исправление, прозрачные расчёты | Гарантированного распознавания скрытых действий, определения ремонтов и пересменок по изображению |

Не начинать с большой системы диспетчеризации, React-фронтенда, микросервисов или облачного inference. Сначала реализовать и проверить v0.1. В v0.1 страницы будущих функций должны быть скрыты или явно недоступны, а не заполнены демонстрационными цифрами.

## 1. Задача и исходный материал

Пользователь хочет анализировать работу экскаватора и обслуживаемых им самосвалов по видеозаписи, впоследствии — по потоку камеры. Нужны обнаружение объектов, последовательности действий, число разгруженных ковшей и длительность операций.

Референс первого пилота: `https://www.youtube.com/watch?v=kjWsR2lVeek`.

По сообщению пользователя, в выбранном ролике камера статична и план не меняется. В предыдущем обсуждении он выбран как запись погрузки CAT 336 в CAT 745. Это контекст пилота, а не сведения, уже измеренные программой. Точную длительность, FPS, разрешение, число заездов и видимость ковша определить после получения файла. Не зашивать эти величины в код.

**Основной вход — локальный видеофайл.** Ссылка YouTube хранится как источник, но не подменяет MP4. Не требовать API-ключ YouTube и не строить основной workflow вокруг загрузчика. Если файла ещё нет, интерфейс и CLI должны сообщить, куда его положить. Не обходить ограничения доступа и не публиковать исходник или кадры автоматически.

Первый пилот ограничен **одним работающим экскаватором в одной сцене**. В кадре могут одновременно находиться несколько самосвалов. Геометрия гидравлического экскаватора из этого ролика и канатного экскаватора на ранее присланных кадрах различается; переносимость между ними здесь не считается проверенной.

Пользователь работает на Mac. Точные чип и память не установлены. Программа сама проводит диагностику устройства; не предполагать наличие NVIDIA, определённого Apple-чипа или заданного объёма RAM.

| Оценка детекции | COCO-compatible evaluator, например `pycocotools` | Независимый расчёт по сохранённым предсказаниям с явным сопоставлением классов |

RF-DETR Nano и Small обозначены разработчиком как Apache 2.0; XL/2XL имеют другие условия и в этот проект не входят [S1]. На дату подготовки PyPI публикует RF-DETR 1.11.2 [S2].

Версии остальных библиотек подобрать совместно с RF-DETR на реальном окружении, затем закрепить `uv.lock`. Не выдумывать проверенный lock-файл заранее. Не устанавливать `develop`/`main` вместо стабильного релиза без конкретной причины. Если 1.11.2 несовместим с окружением, зафиксировать ошибку и обоснованную замену в `docs/DECISIONS.md`, повторить smoke tests и обновить lock.

Новый код трекинга должен использовать `from trackers import ByteTrackTracker` и метод `update()`. В документации Supervision `sv.ByteTrack` помечен устаревшим [S3–S5]. Вызывать RF-DETR напрямую: пакет `inference`, Roboflow-аккаунт и hosted endpoint для этого проекта не нужны.

**Не добавлять в обязательные зависимости:** Ultralytics, SAM, Grounding DINO, VLM/LLM, MLflow-server, Redis, Celery, FastAPI, React, Docker для самого приложения. CVAT может работать отдельно в Docker. Наличие и лицензия конкретной сборки Docker/FFmpeg и транзитивных зависимостей проверяются отдельно; нельзя объявлять весь набор зависимостей «целиком Apache 2.0».

## 3. Архитектура

```text
Локальный MP4
    ↓
Media import / ffprobe / PTS index / scene metadata
    ↓
Разбиение целых эпизодов → train / validation / test
    ↓
Отбор кадров → CVAT → проверенная разметка → COCO snapshot
    ↓
RF-DETR fine-tuning → model bundle + evaluation
    ↓
VideoReader → DetectorAdapter → FrameDetections
    ↓
VehicleTracker + BucketAssociator + BedTruckAssociator
    ↓
Сохранённые наблюдения / треки / диагностические признаки
    ├── Видео с рамками, ID и траекторией
    ├── Проверка качества и очередь ошибок
    └── v0.2: EventEngine → проверка человеком → KPI
```

Вычислительное ядро не импортирует Starlette, Jinja2 или Streamlit. UI и CLI вызывают одни и те же сервисы. Детектор, трекинг, логика событий и расчёт показателей — независимые модули. Повторный расчёт событий по сохранённым детекциям не должен повторно запускать нейросеть.

Хранить три разных уровня данных:

- **Observation:** что действительно обнаружено на данном кадре.
- **Inference:** что алгоритм предполагает по последовательности наблюдений.
- **Review:** что человек подтвердил, исправил или отклонил.

Не перезаписывать первый уровень вторым и не выдавать сглаженные/предсказанные координаты за обнаружение.

## 5. Пользовательский workflow v0.1

1. Создать проект, добавить MP4, увидеть превью, длительность, FPS и диагноз оборудования.
2. Посмотреть короткий участок с исходными COCO-предсказаниями. Этот режим подписан **«Базовая модель, не обучена на наших классах»**.
3. Разметить крупные эпизоды/заезды для разбиения и зафиксировать train/validation/test.
4. Сформировать пакет кадров, разметить его в CVAT и импортировать COCO JSON.
5. Проверить импорт: правильность классов и рамок, количество проверенных кадров, наличие пустых и исключённых кадров.
6. Выполнить короткую проверку обучения, затем полноценное дообучение.
7. Выбрать конкретную сохранённую модель и запустить анализ видео или участка.
8. Просмотреть рамки и траекторию, открыть пропуски/ошибки, выгрузить видео и таблицы.
9. Добавить сложные кадры **из train-части**, исправить разметку и обучить новую версию.
10. После выбора модели и порогов выполнить отдельную финальную проверку на test.

Это интерактивный исследовательский workflow. На первом цикле человек размечает данные; обещать полностью автоматическое обучение без разметки нельзя.

## 6. Импорт видео и время

### 6.1. Входные данные

Поддержать локальные MP4/MOV/MKV, если их декодирует установленный backend. Для первого пилота приоритет MP4. В UI основной способ — выбор/ввод локального пути в рамках разрешённых директорий. Дополнительно — загрузка небольшого файла через браузер.

Не загружать весь длинный ролик в RAM. Ограничение загрузки через браузер — 8192 MiB; его документировать и не повышать без причины [S10]. Большое видео обрабатывать по пути на диске.

Сохранить: `video_id`, исходное имя, SHA-256, размер, duration, width/height, rotation, SAR/DAR, codec, nominal/average FPS, time base, исходный URL при наличии. Метаданные извлекать ffprobe [S11]. Если видео не открывается, возвращать конкретную диагностическую ошибку.

### 6.2. Единая шкала времени

Во всех событиях использовать **секунды относительно начала исходного видео**. Основа — PTS декодированного кадра с учётом time base; сохранить исходный start offset.

`frame_index / fps` допустим только как явно отмеченный fallback для проверенного constant-frame-rate файла. Для variable-frame-rate файла не считать эту формулу точным временем.

Каждому обработанному кадру соответствуют:

```text
video_id, source_frame_index, source_pts, time_base,
source_time_s, analysis_index, width, height
```

Если анализируется фрагмент от 300-й секунды, первое событие не должно внезапно получить timestamp 0. Preview может начинаться с нуля, но его карта времени должна связывать preview time с source time.

Интервалы в БД — полуоткрытые `[start_s, end_s)`. Отрицательные длительности, убывающие timestamp и повторная обработка одного исходного кадра запрещены. Повреждённые участки отмечаются, а не превращаются в простой техники.

### 6.3. Частота обработки

Стартовая частота детекции — **5 кадров/с**, настраиваемая. Для исследования коротких действий в v0.2 предусмотрено 10–15 кадров/с после замера скорости. Это параметры эксперимента, не обещание достаточной точности.

Выбирать кадры по временной сетке, сохраняя их реальные PTS. При нерегулярном шаге передавать трекеру timestamp; не путать FPS исходника, частоту анализа и FPS экспортного видео [S5, S6].

Экспортированный ролик не должен ускоряться из-за пропуска кадров: 5 обработанных кадров в секунду записываются с соответствующей временной шкалой, а не с исходными 30 FPS. Для CFR preview допустимо повторить изображение на его display-интервал, но повтор не создаёт нового наблюдения. Записать `preview_time_map.csv`; при большом пробеле показывать «нет наблюдения».

Проверка: длительность preview соответствует выбранному исходному интервалу с допуском в один выходной кадр. Не требовать сохранения аудио в первом annotated export.

## 7. Классы объектов и правила разметки

Обязательны четыре класса. Внутренние ID приложения — 0–3. COCO `category_id` и выходные индексы модели сопоставляются отдельной проверенной таблицей, а не предположением о нумерации.

| ID | Класс | Название в UI | Что охватывает рамка |
|---|---|---|---|
| 0 | `excavator_body` | Экскаватор: корпус | Кабина, поворотная платформа/противовес и видимая ходовая часть; **без стрелы, рукояти и ковша** |
| 1 | `bucket` | Ковш | Видимая металлическая часть ковша, включая зубья; без рукояти, падающей породы и тени |
| 2 | `haul_truck` | Самосвал | Вся видимая машина: кабина, шасси, колёса и кузов |
| 3 | `truck_bed` | Кузов самосвала | Видимый грузовой кузов как конструкция; не только поверхность груза или открытый проём |

Почему `excavator_body`, а не огромная рамка всей машины: нужен устойчивый ориентир, который не меняет размер вместе с вылетом стрелы. При необходимости полную рамку машины можно добавить отдельным классом в новой версии схемы.

Вложенные рамки `truck_bed` внутри `haul_truck` корректны. Кросс-классовое подавление рамок не должно удалять кузов. Ковш и корпус также не объединяются в один объект.

Дополнительные атрибуты разметки:

```text
visibility = clear | partial | unlabelable
truncated = true | false
instance_local_id = optional string
review_status = unreviewed | reviewed | excluded
annotator, reviewed_at, note
```

Размечать **видимые границы**, а не предполагаемую полную геометрию скрытого объекта. Если объект узнаваем и границы видимой части можно уверенно указать, ставить рамку и `partial`. Полностью скрытый или неразличимый ковш не получает выдуманную рамку.

Если из-за неоднозначности нельзя полноценно разметить все целевые объекты кадра, в v0.1 исключить такой кадр из обучения детектора и обычной оценки детекции. Сохранить его для анализа последовательности и проверки обработки неизвестности. Не превращать неразмеченный видимый объект в отрицательный пример. Реализация ignore-region loss не входит в первую версию.

Проверенный кадр без целевых объектов допустим как настоящий negative; отсутствие разметки у непроверенного кадра — не negative. Не требовать заданного процента полностью пустых кадров: на статичном видео экскаватор может присутствовать постоянно.

Подробная инструкция для человека — `docs/ANNOTATION_GUIDE.md`. Классы «полный ковш», «пустой ковш», «подъезд», «разгрузка», «пересменка» не смешивать с четырьмя классами детекции.

## 8. Разбиение датасета без утечки соседних кадров

**Запрещено случайно перемешивать кадры одного видео и затем делить их на train/test.** Сначала делятся целые временные эпизоды, и только потом из них отбираются изображения.

Единица разбиения — целый заезд/эпизод погрузки самосвала, включая связанные ковшовые циклы. Длинное ожидание между заездами может быть отдельным эпизодом. `split_group_id` объединяет эпизоды, которые нельзя разрывать, например одновременно обслуживаемые/пересекающиеся заезды.

Предложение по долям: train 60%, validation 20%, test 20% по времени/эпизодам, а не требование точного процента каждого кадра. Первоначально программа предлагает три последовательных временных блока; человек сдвигает границы к границам эпизодов. У одного `split_group_id` только один split.

Вблизи разделяющих границ оставить защитный интервал минимум 10 секунд; если операция пересекает границу, целиком перенести её в один split и увеличить буфер. Пересекающиеся окна временной модели в будущем также должны оставаться в одном split.

В интерфейсе — таблица начала/конца и кнопка **«Зафиксировать разбиение»**. Результат — immutable `split_manifest.json` с хешем. Ни sampler, ни CVAT importer не вправе пересчитывать split случайным образом.

Если заездов слишком мало для трёх содержательных частей, программа сообщает ограничение. Не создавать фиктивную независимость: можно использовать временные блоки для технической проверки, но отчёт должен назвать это проверкой на той же сцене, а не переносимостью.

### Роли трёх частей

- **Train:** обновление весов, расширение разметки, отбор сложных случаев.
- **Validation:** выбор checkpoint, learning settings, confidence и tracking/event thresholds.
- **Test:** только финальная оценка зафиксированных весов и параметров.

Отдельный Calibration split для v0.1 не нужен: здесь нет обязательного обучения калибратора вероятностей. Score детектора и rule score не называть вероятностью правильного события. Если позднее появится калибровка уверенности, её данные нельзя брать из test.

Встроенное обучение не должно автоматически читать test после каждой эпохи или после каждого запуска. В RF-DETR отключить test stage (`run_test=False` через поддерживаемый API/конфигурацию); проверить отсутствие test-путей в фактически прочитанных данных. Финальная оценка — отдельная команда. Нельзя незаметно подставлять validation вместо отсутствующего test [S7].

## 9. Отбор кадров и цикл разметки

Первый диагностический пакет — примерно **80 кадров: 60 train + 20 validation**. Он нужен для проверки импорта и короткого обучения, не для заявления итоговой точности.

Первый содержательный набор — ориентировочно **320 кадров: 200 train + 60 validation + 60 test**. При большом числе ошибок расширить примерно до **600: 360/120/120**. Эти числа — план нагрузки для эксперимента; недостаточные данные не компенсируются формальным достижением квоты.

Train sampling должен покрывать положение ковша у забоя, в переносе, над кузовом, в возврате; прибытие, маневрирование, погрузку и выезд самосвала; частичные перекрытия, пыль и тени. Не размечать сотни одинаковых соседних кадров.

Validation/test отбирать по заранее зафиксированному репрезентативному правилу, например равномерно по эпизодам с разными фазами. Не превращать test только в удобные, хорошо видимые кадры или только в сложные ошибки. Сохранить распределения и причины исключения.

Между обычными выбранными кадрами одного эпизода стремиться выдерживать 2 секунды; для редких положений допускается более частый отбор, помеченный причиной. Проверка near-duplicates — предупреждение: на статичном фоне глобальный perceptual hash может не заметить важное изменение маленького ковша, поэтому автоматически выкидывать такие кадры нельзя.

После первой модели добавить active-learning sampler: низкая уверенность, пропадание ковша при видимой рабочей зоне, скачки координат, неоднозначная привязка кузова, ложные срабатывания. **Дополнять им только train.** Сохранять `selection_reason` и модель, которая предложила кадр.

Предразметка необязательна. Первые рамки можно поставить вручную; последующие предлагает собственная дообученная модель. Непроверенные предложения не становятся автоматически ground truth. Validation/test желательно размечать без показа предсказаний оцениваемой модели, чтобы не закреплять её ошибки.

## 10. CVAT и обмен COCO

Поставлять инструкции по CVAT Community согласно официальному руководству установки [S9], а не требовать платного аккаунта. Не запускать CVAT-контейнеры и обучение одновременно по умолчанию на машине с неизвестной памятью.

Приложение экспортирует `annotation_batch.zip`:

```text
images/<stable_frame_id>.jpg
frames_manifest.csv
labels.yaml
annotation_instructions.md
predictions.coco.json             # Опциональная предразметка, явно не ground truth
```

Имена кадров включают `video_id` и исходный индекс. В манифесте дополнительно есть PTS/time, episode, split, image hash. CVAT не должен менять принадлежность split; импорт восстанавливает её по манифесту, а не по имени CVAT subset.

CVAT поддерживает COCO bounding boxes и пользовательские атрибуты; его структура ZIP отличается от структуры, ожидаемой RF-DETR [S8]. Нужен явный конвертер, а не простое переименование архива:

```text
dataset_version/
├── train/
│   ├── _annotations.coco.json
│   └── *.jpg
├── valid/
│   ├── _annotations.coco.json
│   └── *.jpg
├── test/
│   ├── _annotations.coco.json
│   └── *.jpg
├── class_mapping.json
├── split_manifest.json
└── dataset_manifest.json
```

Такой COCO layout описан RF-DETR [S12]. Хранить исходный CVAT export отдельно. Актуальный master-набор включает сведения о review/visibility; обучающий COCO содержит только разрешённые кадры и поддерживаемые поля.

При импорте проверить:

- Существование каждого изображения, его размер и соответствие hash исходному кадру.
- Корректность `image_id`, `annotation_id`, `category_id`, отсутствие дубликатов.
- `bbox = [x, y, width, height]` в пикселях; положительные размеры и нахождение внутри изображения.
- Сопоставление классов **по именам** и сохранённой карте. Не считать class 0 фоном автоматически.
- Полный review кадра, отсутствие неизвестных классов и пересечений split-групп.
- Отличие `reviewed empty` от `unreviewed`; наличие хотя бы нескольких примеров каждого нужного класса в train и validation.

Ошибки отображать с конкретными frame ID. Не исправлять неизвестную категорию «ближайшей похожей». Не использовать `iscrowd=1` как замену неизвестности или окклюзии.

Обязательный round-trip test: изображение → CVAT-compatible COCO → импорт → RF-DETR layout. Координаты и категории должны сохраниться. Атрибуты, не поддержанные экспортом, сохранять в sidecar, а не терять молча.

## 11. Диагностика оборудования

Команда `doctor` создаёт `environment_report.json` и показывает в UI:

```text
OS, Python, CPU architecture, RAM,
torch/torchvision/rfdetr/trackers/supervision versions,
CUDA available, MPS built/available,
FFmpeg/ffprobe availability,
model loading test, inference test, training-step test,
measured latency / peak memory when measurable
```

Автовыбор inference: CUDA → MPS → CPU. Автовыбор training: та же последовательность, но только после успешного реального forward/backward/optimizer step на выбранном backend.

MPS — GPU-backend PyTorch для подходящих Mac; наличие backend само по себе не гарантирует работоспособность всех операций конкретной модели [S13]. В документации RF-DETR CPU/MPS требуют целочисленный batch size, а не `batch_size="auto"` [S14].

Если MPS не поддерживает операцию или не хватает памяти:

1. Зафиксировать исключение и фактическую конфигурацию.
2. Предложить Nano / batch 1 / меньший допустимый resolution либо явно выбранный CPU.
3. Повторный запуск проводить как отдельный run с новой конфигурацией.
4. Не подменять долгую тренировку CPU-режимом без видимого уведомления.

CPU используется как совместимый режим проверки; обещать быструю полноценную тренировку на нём нельзя. Экспорт датасета и train-config для будущего Linux/CUDA — обязательный; самостоятельная аренда GPU и передача данных в облако — нет.

## 12. Обучение RF-DETR

### 12.1. Адаптер модели

`DetectorAdapter` изолирует конкретную библиотеку:

```python
class DetectorAdapter(Protocol):
    def predict(self, frame_rgb: np.ndarray, timestamp_s: float) -> FrameDetections: ...
    def metadata(self) -> ModelMetadata: ...
    def close(self) -> None: ...
```

Публичный результат содержит рамки в координатах исходного изображения, собственные class ID, score и происхождение checkpoint. Если preprocessing меняет масштаб/добавляет padding, обратное преобразование покрыть тестом. Не растягивать bbox самостоятельно поверх уже преобразованного результата библиотеки. Проверить RGB/BGR на интеграционном тесте.

Дообучение реализовать стандартным API RF-DETR, не переписывать training loop без необходимости [S7]. Исходная модель предоставляет обученную визуальную основу, голова адаптируется к нашей схеме. Не замораживать автоматически весь backbone и не ограничивать обучение последним слоем без отдельного эксперимента.

### 12.2. Стартовые профили

| Параметр | Smoke | Pilot Small |
|---|---:|---:|
| Вариант | RF-DETR Nano | RF-DETR Small |
| Resolution | 384 | 512 |
| Epochs | 2 | до 50 |
| Physical batch на Mac | 1 | 1; увеличить только после замера |
| Gradient accumulation | 1 | 4 |
| Learning rate | 0.0001 | 0.0001 |
| Encoder learning rate | 0.00001 | 0.00001 |
| Early stopping | выключен | patience 12, min delta 0.001 |
| Пропуск начальных эпох для best selection | 0 | 3 |
| Workers на Mac | 0 | 0 первоначально |
| Precision на Mac | FP32 | FP32 первоначально |
| Seed | 42 | 42 |
| Test во время train | выключен | выключен |

Это **наши стартовые настройки**, не универсально оптимальные значения. Параметры проекта из YAML переводить в проверенный API адаптера; не передавать произвольные поля YAML прямо в `model.train(**config)`.

В RF-DETR текущая настройка FP32 задаётся `amp_dtype=None`; constructor-only параметры, например `gradient_checkpointing`, не передавать как train kwargs [S14]. Не включать FP8, `torch.compile`, CUDA graphs и ONNX/CoreML export в первый проход. Не пытаться применять CUDA-оптимизации к MPS.

Использовать раннюю остановку и выбор checkpoint только по validation. Целевая библиотечная метрика выбора — box mAP50:95; отдельно контролировать качество ковша, чтобы высокий результат крупного неподвижного корпуса не скрывал проблему. Если датасет слишком мал для устойчивого выбора, отчёт это отмечает.

### 12.3. Аугментации

Только для train: умеренные изменения яркости/контраста, небольшой масштаб/crop при сохранении корректных bbox, горизонтальное отражение при корректном обновлении геометрических метаданных. Не использовать вертикальное отражение, сильную перспективу или вырезание целого ковша как безусловно полезное преобразование.

Для первого smoke оставить простую воспроизводимую схему и сохранить несколько примеров «до/после». Для pilot — явно зафиксированный augmentation preset, совместимый с установленным API [S15]. Validation/test проходят только детерминированный model preprocessing.

Аугментация одного ракурса не считается заменой данных с другой стороны машины.

### 12.4. Контроль до длинного запуска

Провести проверку на 20–40 хорошо размеченных train-кадрах: модель должна уметь заметно подогнаться под этот маленький набор. Это диагностический overfit-test для поиска ошибок данных/классов; не использовать его метрики как качество на новых данных.

Реальный training smoke должен изменить веса и создать загружаемый checkpoint. Не считать наличие пустой папки, конфига или картинок с фиктивными рамками успешным обучением.

### 12.5. Model bundle

```text
models/<model_version>/
├── weights.pth
├── training_checkpoint.ckpt        # Если нужен resume
├── model_config.json
├── class_mapping.json
├── resolved_train_config.json
├── dataset_manifest.json
├── environment_report.json
├── metrics_history.csv
├── validation_metrics.json
├── model_card.md
└── checksums.json
```

Сохранять variant, resolution, порядок классов, библиотечные версии и хеш датасета. Проверять загрузку checkpoint в свежем процессе и совпадение класса/разрешения. Не путать облегчённые inference weights с полным checkpoint для resume [S7].

В model card: область применения, использованный ракурс, тип техники, разбиение, исключённые условия, реальные метрики и отсутствие/наличие проверки на других камерах.

## 13. Детекция и трекинг на видео

### 13.1. Базовый и обученный режимы

Режим `baseline_coco` отображает реальные названия классов исходной модели и не вызывает бизнес-аналитику. Если модель ошибочно назвала экскаватор `truck`, приложение не должно переименовать этот class ID в `excavator_body`.

Режим `custom` доступен только при наличии совместимого model bundle с четырьмя нужными классами. Отсутствие checkpoint — ошибка с инструкцией, а не повод подставить baseline или mock.

### 13.2. Scores и трекеры

Стартовые пороги: raw detection floor 0.10, display threshold 0.35. Для ByteTrack первоначально high-confidence split 0.35 и activation 0.45; проверить совместимость с установленной версией и подобрать на validation.

Не фильтровать все слабые детекции высоким display-порогом до трекера: ему нужны score и low-confidence предложения для второй стадии ассоциации [S5]. Объект с небольшим score может поддержать существующий трек, но не обязан отображаться как надёжное наблюдение или участвовать в событиях.

Для `haul_truck` и `excavator_body` — независимые экземпляры ByteTrack. ID в итоговых данных имеет namespace: `(run_id, video_id, view_id, object_class, local_track_id)`. Не запускать class-agnostic трекинг всех вложенных частей одной машины.

Хранение потерянного vehicle track — стартово 2 секунды, подтверждение нового — 2 наблюдения. В актуальном `trackers` lost buffer задан в кадрах эталонных 30 FPS: 2 секунды соответствуют 60 единицам `lost_track_buffer`, а не 10 только потому, что анализ идёт в 5 FPS [S6]. Преобразование секунд в API вынести в адаптер и покрыть тестом.

Передавать timestamp каждого исходного кадра в `update()` при поддерживаемом API. На новом видео, после seek/перезапуска анализа или смены сцены сбрасывать трекеры. Смена confidence в UI не изменяет уже сохранённый run; создаётся новый запуск/пересчёт.

### 13.3. Ковш

Ковш не обязан хорошо отслеживаться теми же motion-параметрами, что самосвал. Для v0.1 использовать отдельный `BucketAssociator`:

- Выбирать наблюдения класса `bucket`, привязывать их к рабочему экскаватору.
- При нескольких кандидатах учитывать score, близость к последней позиции, допустимую рабочую область и continuity. Пороги нормировать размером корпуса/объекта, а не фиксированным числом пикселей.
- Если кандидаты сопоставимы или принадлежность неясна, возвращать `ambiguous`, а не брать произвольно первый.
- Хранить наблюдаемую траекторию за последние 5 секунд. Не соединять прямой линией участки через большой пробел.
- Короткая экстраполяция допустима только для отображения пунктиром, с флагом `predicted`; по умолчанию не дольше 0.4 секунды. Она не участвует в подтверждении разгрузки.

При одном экскаваторе bucket получает логическую связь с ним, но `bucket_observation_id` сохраняется отдельно от ID корпуса. При появлении второго активного экскаватора программа должна предупредить об ограничении пилота; не привязывать автоматически все ковши к первому.

### 13.4. Кузов и самосвал

`truck_bed` привязывается к наблюдаемому `haul_truck` по доле рамки кузова внутри рамки машины, расстоянию центров, временной стабильности и однозначности назначения. Простого максимума IoU недостаточно для вложенного кузова: он заметно меньше целой машины.

Назначение one-to-one: один кузов не может одновременно принадлежать двум самосвалам. При перекрывающихся машинах и близких оценках сохранить `parent_track_id=null` и `ambiguous=true`.

Положение bbox кузова — не доказательство геометрического контакта ковша с кузовом и не доказательство разгрузки в 3D.

### 13.5. Наблюдаемость

У каждого шага есть `observed | weak | predicted | missing | ambiguous`. `missing` означает отсутствие надёжного наблюдения, а не физическое отсутствие объекта.

Разделить причины: no_detection, low_confidence, occluded_if_known, out_of_frame_if_known, decode_gap, ambiguous_association. Не утверждать окклюзию как факт только потому, что модель пропустила объект.

## 14. Ракурс и геометрия

Код не должен знать, что «забой слева», а «самосвал справа». Для каждого `view_id` разрешены пользовательские зоны в нормированных координатах `[0,1]`:

```text
working_area, dig_zone, loading_zone, entry_zone, exit_zone
```

В v0.1 зоны необязательны для обычной детекции; в v0.2 они могут помочь правилам пилота. Их сохранение — настройка конкретной камеры, а не обучение нейросети и не универсальное понимание сцены.

Минимальный редактор зон — таблица вершин x/y и превью поверх кадра. Не добавлять тяжёлый canvas-фреймворк только ради первого прототипа. Проверять диапазоны координат, минимум три вершины и ненулевую площадь.

Смена ракурса создаёт новый `view_id`. При перемещении камеры старые зоны недействительны. Автостабилизация дрона, восстановление 3D и многокамерная реконструкция вне v0.1.

Базовый будущий путь переносимости: новые реальные ракурсы → та же схема объектов → дообучение → camera-held-out test. В metadata уже сейчас хранить `site_id`, `camera_id`, `view_id`, `equipment_family`. Проверка на другом временном фрагменте текущего ролика остаётся **same-scene test**.

## 15. Интерфейс

Рабочее название — **Excavation Video Lab**. Интерфейс на русском, код и имена сущностей на английском. Нужны понятные подписи, а не показ всех Python-параметров без объяснений.

### «Видео»

Добавить источник; показать метаданные и hardware report; проиграть видео; выбрать начало/конец; запустить baseline; показать список запусков. При отсутствии MP4 — конкретный путь/кнопка добавления, а не неработающий демоплеер.

### «Данные и разметка»

Таблица эпизодов, split и guard intervals; фиксация разбиения; отбор кадров; contact sheet; экспорт для CVAT; импорт COCO; результаты validation; количество reviewed/unreviewed/excluded. До фиксации split экспорт обучающего snapshot заблокирован.

### «Обучение»

Выбор dataset version, Nano/Small, hardware, профиля; оценка по короткому benchmark; Start/Cancel; status, epoch, реальные loss/validation metrics и путь к checkpoint. По умолчанию показывать небольшое число настроек, остальные — в Advanced.

Не рисовать loss-кривую до появления реальных training logs. Не показывать ETA, пока нет измеренного времени нескольких шагов.

### «Анализ»

Выбор bundle и диапазона; analysis FPS; параметры отображения; запуск; preview результата. Переключатели рамок, классов, scores, ID, траектории и зон. Отображать source timestamp, model version и текущую долю наблюдаемых кадров.

Рабочее видео — закодированный MP4 через HTTP Range. Диагностика — один кадр и таблица. Прогресс — последующий запрос, который читает атомарный progress JSON [S16].

### «Качество»

Per-class metrics; число проверенных кадров и GT-объектов; visibility strata; ошибки; сравнение двух runs на одном dataset hash. Кнопка «Отправить в разметку» работает только с train; test не становится очередью дообучения.

### «События» — v0.2

Временная шкала и таблица event candidates; переход к короткому фрагменту до/после события; Confirm / Reject / Correct time / Assign truck visit / Add missed event. Ручные изменения в отдельном audit log. Показ подтверждённого и оценочного счётчика раздельно.

Для точных действий не полагаться только на округляемый seek браузерного плеера: должен быть просмотр кадров около события с точными исходными timestamp.

## 16. Фоновые задания и хранение

Тренировку и длинный inference запускать в отдельном процессе. Один GPU/MPS job одновременно; второй клик или второй запрос не запускает ещё один. UI не должен держать вторую копию модели при работающем worker.

SQLite хранит jobs, media, dataset/model versions, manifests и review. Worker пишет progress JSON атомарно и журнал в run directory. Большие покадровые результаты сохраняются порциями в Parquet.

Статусы: `queued`, `running`, `completed`, `failed`, `cancel_requested`, `cancelled`. Статус completed устанавливается только после завершения обработки, закрытия encoder и проверки обязательных артефактов.

Cancel должен останавливать процесс и освобождать память; частичный результат имеет явный `partial=true` и реальный analyzed_end_s. После падения UI фоновые job не должны дублироваться при повторном открытии. Проверять PID/lock и отражать orphaned/failed состояния.

Не разрабатывать распределённый scheduler. Для первого приложения достаточно одного локального worker и файлового/SQLite-lock. Все команды запускаются без `shell=True` с аргументами-массивами.

## 17. Схемы результатов

### 17.1. `frame_status.parquet`

Одна запись на обработанный исходный кадр, включая кадры без объектов:

```text
run_id, video_id, view_id, source_frame_index, source_time_s,
decode_status, analyzed, model_version, inference_ms,
num_detections, bucket_observation_state, diagnostic_flags
```

Без этой таблицы пустой кадр нельзя отличить от непроведённого анализа.

### 17.2. `detections.parquet`

```text
run_id, observation_id, video_id, view_id,
source_frame_index, source_time_s,
class_id, class_name, score,
x1, y1, x2, y2, frame_width, frame_height,
track_id_nullable, parent_track_id_nullable,
observation_state, association_score_nullable, model_version
```

Только результаты детектора данного кадра. Предсказанные позиции хранятся отдельно в `track_states.parquet` с `is_observed=false`.

### 17.3. `track_states.parquet`

```text
run_id, track_id, class_name, source_time_s,
state, last_observed_time_s, is_observed,
x1_nullable, y1_nullable, x2_nullable, y2_nullable,
parent_track_id_nullable, identity_uncertain
```

### 17.4. `events.csv` — v0.2

```text
event_id, run_id, video_id, view_id,
excavator_id, truck_visit_id_nullable,
event_type, start_s, end_s, anchor_s,
inference_status, rule_score_nullable,
review_status, evidence_observation_ids,
left_censored, right_censored, note
```

`inference_status = candidate | inferred | unknown`; `review_status = unreviewed | confirmed | corrected | rejected`. Это две независимые оси. Score правил не подписывается «вероятность».

### 17.5. `truck_visits.csv` — v0.2

```text
truck_visit_id, video_id, excavator_id_nullable,
linked_track_ids, physical_vehicle_id_nullable,
first_seen_s, in_position_s_nullable,

```

CSV с числами — decimal point, UTF-8; пользовательская выгрузка для Excel может быть UTF-8 BOM. Пустое значение означает неизвестность, а не ноль. При экспорте notes защищать формульные префиксы в ячейках; исходный текст сохранять в БД.

JSON содержит `schema_version`. Координаты и время имеют единицы измерения в schema docs. Изменение схемы — новая версия, не молчаливое переосмысление старых данных.

## 18. Проверка качества

### Детекция

На frozen validation/test рассчитать AP50, AP50:95, precision и recall при выбранном operating threshold, отдельно по каждому классу. Для precision/recall — IoU 0.5 и one-to-one matching. AP считать по исходным детекциям до трекинга/сглаживания, по диапазону scores, а не после высокого display threshold. Для evaluation использовать отдельный низкий score floor, первоначально 0.001, и фиксированный max detections; operational floor 0.10 не должен обрезать PR-кривую оценки.

Отдельно показать число GT-объектов, число оценённых кадров и долю исключённых по labelability. Сравнение «до/после» на разных наборах кадров запрещено. Показать recall отдельно для GT-объектов `clear` и `partial`, если достаточно примеров; matching сначала выполняется на полном GT кадра. Precision и ложные срабатывания считать на полном оценочном домене, не приписывая им вымышленную GT-видимость.

Ориентиры пилота, **не гарантии**: precision/recall самосвала ≥0.90; recall видимого размечаемого ковша ≥0.85 при precision ≥0.85. Результат ниже ориентира — valid экспериментальный результат со списком ошибок, но не промышленная приёмка.

### Трекинг

Выделить несколько полностью размеченных последовательностей validation/test, покрывающих поездку/перекрытие машин. Начальный ориентир — суммарно 2–3 минуты из отложенных эпизодов, насколько позволяет ролик. Ground-truth tracks размечаются отдельно от редкой детекционной разметки.

Считать ID switches и фрагментацию в наблюдаемые интервалы. IDF1/HOTA включать только при корректной полной GT-разметке и проверенном evaluator; иначе показывать `not evaluated`. Не выводить эти метрики по неполной разметке и не маскировать отсутствие GT.

### Время и производительность

Проверить source timestamps, сохранение длительности preview, корректность начала анализируемого фрагмента. Замерить throughput на реальном железе: decoding, inference, postprocess, encoding и общее время. Скорость обработки offline и возможность real-time — разные выводы.

### События — после v0.1

Сопоставлять predicted и GT unload events one-to-one с допуском anchor-time первоначально ±1 секунду. Считать precision/recall/F1 событий, ошибку количества по каждому заезду, MAE временных границ и долю unknown.

Не ограничиваться суммарной ошибкой числа ковшей: один пропуск и одно ложное событие могут дать правильный итоговый счёт. Оценивать **сырые автоматические события до ручных исправлений** и итог после review раздельно. Нельзя оценивать подсказки по GT, созданной только подтверждением тех же подсказок: человек должен также находить пропуски по полному фрагменту.

## 19. Автоматические тесты и критерии готовности v0.1

Обязательные unit/integration tests:

1. COCO `xywh` ↔ internal `xyxy`, class mapping и resize/padding inverse.
2. Reviewed empty / unreviewed / excluded различаются; неизвестные категории не принимаются.

8. ByteTrack получает реальные scores; расчёт lost buffer в секундах корректен.
9. Перекрывающиеся `haul_truck`/`truck_bed` не подавляются и не меняются классами.
10. Потеря наблюдения ковша не создаёт обычную «observed» рамку или событие.
11. При смене источника/seek треки сбрасываются; ID двух videos/runs не сталкиваются.
12. У одного кузова не бывает одновременно двух родителей; ambiguous сохраняется.
13. Второй клик или второй запрос не запускает вторую тренировку; Cancel завершает worker.

Синтетические fixtures разрешены для проверки математики, интерфейсов и pipeline mechanics. Они явно помечены и не служат доказательством точности на карьерном видео.

**v0.1 функционально готова**, когда пользователь может провести весь workflow от локального MP4 и проверенных labels до настоящего checkpoint, отдельной оценки и annotated video. Отдельно фиксируется, достигнуты ли ML-цели. «Приложение работает» и «модель уже достаточно точна» — два разных пункта приёмки.

## 20. Расширение v0.2: действия и события

Не обучать отдельную временную нейросеть на старте. Сначала использовать прозрачную последовательность наблюдений и ручной review. Модуль выключен, пока нет пригодного custom detector и проверенных time/association outputs.

### 20.1. Три параллельных уровня

**Состояние экскаватора:** `loading`, `working_unclassified`, `stationary_no_truck_observed`, `stationary_reason_unknown`, `repositioning`, `unknown`.

**Фаза ковша:** `digging_candidate`, `transfer_to_bed_candidate`, `dump_candidate`, `return_candidate`, `unknown`.

**Состояние самосвала:** `approaching`, `manoeuvring`, `in_position`, `being_loaded`, `departing`, `unknown`.

Фазы ковша вложены в деятельность экскаватора; состояния самосвала идут параллельно. Нельзя складывать их длительности в один баланс смены, получая больше 100% времени. Для главной временной шкалы экскаватора на каждый интервал задаётся одно состояние, включая `unknown`.

По одним рамкам в v0.2 обычно можно предложить геометрические фазы, но не доказать физическое наполнение/разгрузку. `face_preparation`, `shift_change`, `maintenance`, `breakdown` автоматически не назначаются. Человек может добавить подтверждённую причину отдельным полем и источником.

### 20.2. Кандидат разгрузки

Пример цепочки для пилота:

```text
Наблюдение ковша у dig_zone
→ движение от забоя
→ наблюдаемый ковш около связанного кузова
→ короткое пребывание/изменение движения
→ уход от кузова и возврат к рабочей зоне
```

Такая цепочка создаёт **inferred unload candidate**, а не достоверный факт выгрузки материала. Пересечение двух прямоугольников без временной цепочки — только слабый candidate. Видимость падающей породы, поворот ковша и заполненность не являются выходами текущего четырёхклассового детектора; не притворяться, что модель уже умеет их определять.

Человек смотрит короткий фрагмент и подтверждает фактическую разгрузку. Позднее на этих проверенных видеоотрезках можно обучить action classifier/pose/segmentation-модель, но это отдельный этап с отдельной оценкой.

Кандидат требует однозначной связи с кузовом и заездом. При потере ковша/кузова в критическом интервале вернуть unknown. Не восстанавливать «пропущенный ковш» только из среднего периода цикла.

Дедупликация: один подход с тем же набранным материалом → одно событие, даже если оператор несколько раз встряхнул ковш над кузовом. Для нового события требуется новый цикл/возврат, а не только истечение таймера. Разгрузка одного набора в разные машины — нестандартный случай для ручной проверки.

Все thresholds задаются в секундах или нормированных геометрических величинах в `view_config`; defaults — экспериментальные. Debug view показывает, какие наблюдения и правила породили candidate.

### 20.3. Заезд самосвала и идентичность

`track_id` — технический ID непрерывного визуального сопровождения. `truck_visit_id` — эпизод обслуживания. `physical_vehicle_id` — настоящий идентификатор машины, который в пилоте может быть неизвестен.

Смена track ID при перекрытии не должна автоматически создавать новый заезд. Связь фрагментов внутри короткой окклюзии может предложить алгоритм, но неоднозначность остаётся видимой. Пользователь может объединить/разделить заезды с записью в audit log.

Самосвал уехал и позже вернулся — новый visit. Нельзя автоматически объявлять его тем же физическим автомобилем только потому, что похож цвет. В первом пилоте KPI считать по заездам; группировка повторных заездов одной машины — ручное дополнительное поле.

Начало/конец видео или анализируемого отрезка может обрезать заезд. Такие visits имеют `left_censored`/`right_censored`. Их доступные ковши можно показывать, но полную продолжительность загрузки по ним считать нельзя.

### 20.4. Ожидание и неподвижность

Нет надёжного наблюдения самосвала — ещё не доказательство, что его нет в рабочей зоне. Состояние `stationary_no_truck_observed` требует видимой рабочей зоны, достаточной уверенности в наблюдении техники и отсутствия значимого движения экскаватора в заданном интервале.

Если ковш работает при отсутствии наблюдаемой машины, это `working_unclassified`, а не ожидание. Неподвижность при стоящем самосвале — `stationary_reason_unknown`. Причины «не хватает транспорта», «ремонт», «пересменка» требуют внешних данных или ручного подтверждения.

## 21. Определения показателей

До появления соответствующих проверяемых событий показывать **«не рассчитано»**, а не 0.

| Показатель | Определение |
|---|---|
| Подтверждённые ковши | Число событий физической разгрузки с review confirmed/corrected и без rejection |
| Оценочное число ковшей | Подтверждённые + непроверенные inferred events; слабые candidates отдельно; каждое event ID учитывается один раз |
| Ковши на заезд | Подтверждённые разгрузки, связанные с конкретным truck_visit_id |
| Ковши экскаватора | Подтверждённые разгрузки, связанные с excavator_id за выбранный интервал |
| Время присутствия самосвала | last_seen − first_seen; для обрезанного визита подписать «наблюдаемая часть» |
| Время обслуживания | departure − in_position, только при известных и подтверждённых границах |
| Окно разгрузок в самосвал | end последней разгрузки − start первой разгрузки; **не называть это полным временем загрузки** |
| Полное время загрузки | От подтверждённого начала первой операции загрузки данного заезда до конца последней разгрузки; при неизвестном начале не рассчитывать |
| Интервал между разгрузками | anchor следующей разгрузки − anchor предыдущей, внутри одного visit, без неизвестного промежутка; это не автоматически полный цикл ковша |
| Полный цикл ковша | Начало набора i → начало набора i+1, при достоверных границах и непрерывной наблюдаемости; межзаездное ожидание учитывать отдельно, не смешивать с чистыми циклами |
| Среднее время на самосвал | Среднее полного времени загрузки по завершённым визитам; отдельно mean/median обслуживания |
| Доля неизвестности | Длительность unknown / длительность анализируемого интервала |

Для средних выводить число пригодных наблюдений и число исключённых. Median/P90 показывать при достаточном числе наблюдений, иначе помечать малую выборку. Не подменять среднюю длительность циклов формулой «длительность всего ролика / число ковшей»: в неё попадут подъезды, ожидания и обрезанные циклы.

Тонны, коэффициент наполнения ковша, объём добычи, производительность т/ч и финансовый эффект в v0.1/v0.2 не вычислять без дополнительных исходных данных и отдельной методики.

## 22. Безопасность, воспроизводимость и права на данные

Приложение слушает только localhost. Нет встроенной аутентификации для внешнего сервера, поэтому не публиковать его наружу как production service. Проверять пути и ZIP entries против path traversal, ограничивать размер распаковки. Не исполнять пользовательские YAML/Python expressions.

Не отправлять видео/кадры/разметку в API, внешние логгеры или облако без отдельного разрешения. Загрузка официальных весов при первом запуске допустима после понятного сообщения о сетевой операции; последующие анализ и обучение должны работать с локальным кэшем. Отключить внешние экспериментальные логгеры и доступную телеметрию.

Пользователь предоставляет файл, который вправе использовать для выбранной цели. Наличие публичной ссылки само по себе не означает разрешение на публикацию учебного датасета. Не включать исходник, кадры, labels, weights, секреты и большие артефакты в Git автоматически. Сохранять provenance и notices зависимостей. Публичную лицензию нового проекта пользователь выбирает отдельно.

Сторонние `.pth/.ckpt` принимать только из доверенного источника; не отключать защитные проверки загрузчика молча. Собственные checkpoints и официальные веса хранить с хешами.

В отчётах разделять: автоматический результат, результат после ручной коррекции, целевой KPI, фактический замер. Никогда не заменять отсутствующие измерения демонстрационными числами.

```bash
uv run excavation events export --project pilot --run RUN_ID
```

CLI отвечает ненулевым exit code при ошибке. В машинном режиме поддержать JSON-result. UI использует тот же service layer. Флаг `--final` требует frozen dataset/model/config; не запускает обучение и не изменяет пороги.

## 24. Этапы исполнения для Cursor

### M0 — Проверяемая основа

Создать проект, зависимости, doctor, схемы, media import, PTS reader, source preview, baseline adapter, unit tests. Проверить реальную загрузку исходного checkpoint и inference на доступном кадре. Если MP4 отсутствует, реализовать import workflow и тесты, не скачивать другой ролик как незаметную замену.

**Приёмка:** импорт/время/превью работают; baseline честно подписан; никаких обещаний детекции пользовательских классов.

### M1 — Данные и разметка

Реализовать episode splits, freeze, sampling, CVAT export/import, dataset validation/snapshot и соответствующие страницы. Подготовить первый пакет кадров из реального файла при его наличии.

**Приёмка:** round-trip COCO проходит, классы/координаты/эпизоды сохраняются, train/test не смешиваются. Пользователь может начать ручную разметку.

### M2 — Реальное обучение

Реализовать training worker, smoke/overfit/pilot profiles, logs, model bundles, checkpoint reload и evaluation. Полноценное обучение запускать только по действительно импортированной проверенной разметке.

**Приёмка:** реальный checkpoint, метрики по фактическим данным и возможность загрузки в новом процессе. При отсутствии labels — функциональный код и явный статус ожидания данных, не фиктивный результат.

### M3 — Детекция и сопровождение

Реализовать analyze pipeline, vehicle tracking, bucket/bed associations, visibility, output видео/таблиц, diagnostics и review ошибок. Проверить начало/середину/конец и полный доступный ролик, измерить время/память.

**Приёмка:** завершённый v0.1 workflow, тест-отчёт с фактическим качеством и ограничениями.

### M4 — Кандидаты циклов и review

После M3 добавить правила событий, visits, review и KPI по определениям этого ТЗ. Не обещать автоматическое различение всех операций. На малой выборке главная ценность — сбор проверенных событий для следующей модели.

**Приёмка:** сырые и исправленные события раздельны, нет двойного счёта, скрытые/обрезанные действия отмечены, статистика проверяется по исходному видео.

## 25. Что Cursor должен передать по окончании

Рабочий репозиторий, README с установкой на Mac, проверенный lock-файл, инструкция разметки, CLI/UI, тесты и `docs/TEST_REPORT.md`.

В TEST_REPORT перечислить точные выполненные команды, версии, данные, полученные артефакты и реальные результаты. Отдельно — что не проверено из-за отсутствия MP4, labels, вычислительного устройства или разметки теста. Скриншот интерфейса и успешный pytest не заменяют проверку обученной модели на видео.

Не создавать commit/push и не менять историю других репозиториев без запроса. Не добавлять AI co-author trailers в сообщения коммитов.
